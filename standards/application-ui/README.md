# Application UI Standard

本ドキュメントは、複数アプリで操作感を揃えるための **Core Application UI Standard** です。
見た目の細部ではなく、「どのUIをどの場面で使うか」という判断を揃えます。実際のコンポーネントコードは別のShared UI等で管理します。

---

## 1. UIの基本原則

- **Primary Action**: 画面の主操作は、原則としてPage Header付近の分かりやすい位置（通常は右側）に置く。画面特性上より適切な配置がある場合は例外を許容する。
- **通知**: `alert()` を通常の通知に使わない。保存成功など、操作後の補助的なフィードバックにはToastを使う。
- **破壊的操作**: `confirm()` に依存せず、重要な削除等はConfirm Dialog等で意図を確認する。
- **Empty State**: データがない場合は空の表だけを出さず、状態を明示する。ユーザーが次に取れる有効な操作がある場合のみ、そのアクションも提示する。
- **再利用**: 共通UIやDomain Componentが存在する場合は、同じ用途のUIを各プロジェクトで再実装しない。

---

## 2. エラーとフィードバックの粒度

エラーの種類に応じて、表示場所と強さを揃えます。

| 種類 | 基本表現 | 例 |
|---|---|---|
| 入力項目のエラー | Field Error | 必須、形式、文字数 |
| フォーム全体・業務ルールのエラー | Form Error / Alert | 状態上この操作を実行できない |
| 操作・非同期処理の一時的失敗 | Toast | 保存失敗、アップロード失敗、通信失敗 |
| ページ・機能自体を利用できない | Error State / Error Page | 対象消失、重大な読込失敗 |

ユーザーが修正しなければならない入力エラーをToastだけで伝えません。
内部例外の詳細やstack traceをそのままユーザーへ表示しません。

---

## 3. フォーム / バリデーションUX

- 必須、形式、文字数など、早く検出できる入力不備は可能な範囲でクライアント側でも知らせる。
- 正当性の最終判断は必ずサーバー側で行う。
- Field Errorは対象フィールドの近くに表示する。
- フォーム全体の業務エラーはフォーム上部等の分かりやすい場所に表示する。
- 送信失敗時に入力内容を不用意に失わない。
- 保存中は必要に応じて二重送信を防止する。
- 保存成功などはToast等で補助的にフィードバックする。
- 必須記号の色や具体的な余白など、見た目の細部はCore Standardで固定しない。

---

## 4. 共通 Domain Components

複数アプリで繰り返すドメインUIや複雑なUIは、Shared UI等で提供されている共通実装を優先します。

代表例:

- 社員選択: `UserPicker` / `EmployeeSearch`
- 組織・部署選択: `DepartmentPicker` / `OrganizationTree`
- 日時選択: `DatePicker` / `DateRangePicker`
- データ一覧: `DataTable`

具体的なライブラリ選定や実装方式は、このStandardsリポジトリではなくShared UI側のRecommendation / 実装ドキュメントで管理します。

---

## 5. Layouts

レイアウトは単なる参考例ではなく、複数アプリ間の操作感を揃えるための **テンプレート標準** とします。

新規アプリ・新規画面は、原則として **Standard App / Simple App / Focus App のいずれかをベースにすること**。AIや開発者が画面ごとにナビゲーション構造をゼロから設計することは避けます。

アプリ固有の要件は、まず既存レイアウトの骨格を保ったまま拡張して対応します。既存レイアウトに適合しない場合でも、すぐに新しい標準レイアウトを追加せず、以下の順で判断します。

1. 既存3レイアウトのいずれかで表現できないか確認する。
2. 既存レイアウトへの拡張（Inspector、Filter Bar、Tabs、補助Toolbar等）で対応できないか確認する。
3. それでもUX上の明確な理由がある場合のみ、プロジェクト固有レイアウトを許容する。
4. 同じ派生レイアウトが複数プロジェクトで繰り返された場合に限り、標準レイアウトへの昇格を検討する。

標準レイアウトの主要骨格を変更する場合は、その必要性を明示します。将来「なぜこのアプリだけ違うのか」が問題になる程度の大きな逸脱はプロジェクト側で理由を記録し、軽微な見た目やコンテンツ構成の変更までADRを要求しません。

### 5.1. Standard App

一般的な業務システム、管理画面、マスタ管理向け。通常の業務アプリでは最初にこのレイアウトを検討します。

**主要骨格（原則維持）**:

- **Global Header**: 画面上部に配置。左側にアプリ/ブランド、右側にUser Menu。
- **Sidebar**: 左側に配置し、アプリ内の主要ナビゲーションを持つ。
- **Main Content**: Sidebarの右側を主作業領域とする。
- **Page Header**: Main Content上部に画面タイトルとPrimary Actionを置く。
- **Primary Action**: 原則としてPage Header領域に配置する。

**拡張可能な要素**:

- Sidebar幅
- Main Contentの最大幅
- Grid / Card構成
- Filter Bar
- Tabs
- 右側Inspector / Detail Pane
- Dashboard Widget
- 補助Toolbar

### 5.2. Simple App

単機能ツール、小規模ユーティリティ、簡易申請など、恒常的なアプリ内ナビゲーションを必要としない画面向け。

**主要骨格（原則維持）**:

- Sidebarを持たない。
- Headerを画面上部に配置し、左側にアプリ名、右側にUser Menuを置く。
- Main Contentを主領域とし、必要に応じて最大幅を制限して読みやすくする。

単に実装量を減らしたいという理由だけでStandard AppからSidebarを削除してSimple App扱いにしません。アプリ内に継続的な主要ナビゲーションが必要ならStandard Appを選びます。

### 5.3. Focus / Tool App

座席表、エディタ、キャンバス、地図、作業画面など、広い作業領域そのものが主要価値となるアプリ向け。

**主要骨格（原則維持）**:

- **Minimal Header**: グローバル操作に必要な最小限のHeaderを上部に持つ。
- **Main Workspace**: 残りの大部分を作業領域として利用する。
- ツール固有の操作はHeaderまたはWorkspace内のToolbar等に集約する。

Focus Appを理由に、ユーザー操作やアプリ間で共通するナビゲーションまで無秩序に独自配置しません。

### 5.4. 強制力の境界

レイアウト標準は「完全固定の画面デザイン」ではありません。

**強く統一するもの**:

- Global Headerの位置と役割
- User Menuの基本位置
- Sidebarの位置と役割
- Page Headerの役割
- Primary Actionの基本配置
- アプリ内ナビゲーションの基本構造

**各アプリで調整してよいもの**:

- 余白、幅、高さなどの細かな寸法
- Content内のGrid / Card / Table構成
- Filter、Tabs、Inspector、Toolbar等の補助UI
- 業務要件に応じた情報密度

この境界により、利用者がアプリごとにナビゲーションを学び直す状態を避けつつ、業務画面として必要な拡張性は残します。

レイアウトの具体的なDjango Template / React実装はShared UI等で管理し、実装が提供されている場合はそれを優先して利用します。
