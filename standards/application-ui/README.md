# Application UI Standard

本ドキュメントは、「複数アプリを利用したときに、ユーザーが同じ操作感で迷わず利用でき、開発時にも毎回UI/UXをゼロから設計しなくてよい状態」を作るための標準を定義します。

**重要な原則**:
* 本ドキュメントは「判断の再利用（ルール）」を定義するものであり、実際のコンポーネントコード（実装）は含みません。
* 各プロジェクトで共通UIライブラリ（別リポジトリ等を想定）から指定のコンポーネントをインポートして利用してください。

---

## 1. UIの基本原則と判断基準

画面設計において、以下の共通ルールを遵守してください。

* **Primary Action の位置**: 画面の主操作（作成・保存など）は必ず右上に配置する（`PageHeader` コンポーネント等を利用）。
* **通知の標準化**: 保存成功・エラーなどの通知は、ブラウザ標準の `alert()` を使わず、必ず `Toast` コンポーネントを使用する。
* **削除の確認**: 削除など破壊的な操作を行う場合は、ブラウザ標準の `confirm()` を使わず、必ず `ConfirmDialog` (モーダル) を使用する。
* **空状態 (Empty State)**: データが存在しない場合は、単に空のテーブルを表示するのではなく、必ず「データがない旨と、次のアクションを促すメッセージ」を含めた Empty State コンポーネントを表示する。

---

## 2. 共通 Domain Components

複数のアプリで共通して登場するドメイン（社員、組織など）や複雑なUIは、それぞれ独自のUIを再実装せず、共通コンポーネントを利用すること。

* **社員選択**: `UserPicker` / `EmployeeSearch` を利用（検索、サジェスト、顔写真表示の統一）
* **組織・部署選択**: `DepartmentPicker` / `OrganizationTree` を利用
* **日時選択**: 複雑な日付選択には `DatePicker` / `DateRangePicker` を利用
* **データ一覧**: 共通の `DataTable` を利用（ソート、ページネーション、フィルターUIの統一）

---

## 3. Layouts (画面レイアウト標準)

画面を新規作成する際、AIにゼロからHTML構造を設計させてはなりません。
アプリの目的に応じて、以下の Layout のいずれかを選択し、それに準拠した構造で実装してください。

### 3.1. Standard App (標準業務アプリ)
一般的な業務システム、管理画面、マスタ管理などに使用する最も標準的なレイアウト。

**画面構造の原則**:
* **Global Header**: 画面最上部に配置。左端に「アプリ名/ブランド」、右端に「User Menu」を置く。
* **Sidebar (左)**: アプリ内の主要なナビゲーションリンクを配置する。
* **Main Content (右)**: サイドバーの右側に広く配置。
  * **Page Header**: Main Content の最上部に「画面タイトル」と「Primary Action（ボタン）」を配置。

### 3.2. Simple App (シンプルツール)
単機能のツール、小規模なユーティリティ、簡易申請画面などに使用する軽量なレイアウト。

**画面構造の原則**:
* サイドバーは持たない。
* **Header**: 画面上部に配置。左端に「アプリ名」、右端に「User Menu」。
* **Main Content**: 画面中央に配置（最大幅を制限して中央寄せすることが多い）。

### 3.3. Focus / Tool App (フォーカスアプリ)
座席表、エディタ、ダッシュボードなど、作業領域（キャンバス）を画面いっぱいに広く取りたいアプリに使用するレイアウト。

**画面構造の原則**:
* **Minimal Header**: 最小限の高さのヘッダーのみ。
* **Main Workspace**: 画面の残りすべての領域をキャンバスとして使用する。アプリ内ナビゲーションはヘッダー内に収めるか、フローティングツールバー等で提供する。
