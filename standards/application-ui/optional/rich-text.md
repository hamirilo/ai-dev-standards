# リッチテキスト入力（構造化文書）

このOptional Standardは、議事録・報告書など、一般ユーザーが見出しやリストを持つ構造化された文書を入力・保存・表示する機能を実装する場合に参照します。

前提となる判断: Markdown記法を一般ユーザーへ要求しない。プレーンテキストでは文書構造が残らない。自由なHTML入力は許可しない。この3つの帰結として、入力はリッチテキストエディタで行う。

保存形式とサニタイズはプロジェクト内で閉じず、後からの移行が最も高くつく判断のため、最初に統一する。

## 1. 入力手段

- リッチテキストエディタをReact Islandとして実装する。ライブラリの既定は [Recommendations](../../../recommendations/frontend.md) を参照する。
- ツールバー・ボタン類はエディタ付属のUIではなく `shadcn/ui` で組み、Core StandardのSemantic Tokenに沿わせる。
- Markdownエディタを一般ユーザー向け画面の入力手段にしない。開発者向け機能でMarkdownを扱う場合は、この文書ではなく用途側で判断する。

## 2. 機能の範囲

初期セットは次に限定する。

- 見出し（2〜3レベル）、段落
- 箇条書き・番号付きリスト
- 太字、リンク
- 表（実際に必要な画面のみ）

次は提供しない。

- **文字色・フォント・文字サイズの自由指定。** 文書の強調は構造（見出し・太字）で表す。装飾の自由度はSemantic Tokenと文書間の一貫性を壊し、後から取り上げることが難しい。
- **画像・ファイルの埋め込み**（ファイルアップロードの扱いが未定義のあいだ）。エディタ機能として先行させず、アップロード境界とセットで判断する。

機能の追加は画面単位ではなくプロジェクト単位で揃える。同じアプリ内でエディタごとにできることが違う状態を作らない。

## 3. 保存形式

- **エディタのJSON表現（ProseMirror Document）を正として保存する。**
- 表示用HTMLは派生データとして扱う。保存時に生成し、**サーバーでサニタイズしてから**保存または配信する。派生である以上、正のJSONからいつでも再生成できる状態を保つ。
- HTMLだけを保存しない。再編集・検索・将来の形式変換に必要な構造を失う。
- 全文検索が必要な場合は、プレーンテキスト抽出を派生カラム等に持つ。

## 4. 表示とセキュリティ

- 閲覧画面はサニタイズ済みHTMLをDjango Templateで表示する。閲覧のためだけにエディタを読み取り専用でマウントしない。
- **クライアント由来のHTMLをサニタイズなしで `|safe` 表示しない。** 保存時のリクエスト改ざんはエディタのUI制限をすり替えるため、stored XSSになる。
- サニタイズは許可リスト方式とし、エディタの機能範囲（§2）が生成しうるタグ・属性だけを許可する。機能を追加したら許可リストも同時に更新する。
- リンクには `rel="noopener"` 等、外部リンクの基本的な保護を適用する。

## 扱わないもの

- ライブラリの選定 — [Recommendations](../../../recommendations/frontend.md)
- エディタのセットアップ手順、拡張のAPI — ai-dev-playbook
- 共同編集、コメント、変更履歴 — 繰り返しが確認されていない。必要になった時点で、有償機能・Cloud前提を含めて個別に評価する。
- 文書のPDF・帳票出力 — 入力とは別の責務としてサーバー側で扱う。方式は別途定義する。
