# 一覧画面

このOptional Standardは、並び替え・絞り込み・ページネーションを伴う一覧／検索画面を実装する場合に参照します。

業務システムで最も繰り返される画面であり、実装手段と操作がプロジェクトごとに違うと、ユーザーはアプリを移るたびに学び直しになります。ここでは判断基準だけを定義し、コンポーネントの実装手順は扱いません。

## 1. 実装手段の選択

| 画面の性質 | 実装 |
|---|---|
| 検索条件を送信して一覧を丸ごと差し替えるだけ。行単位の対話がない | Django Template + htmx |
| ヘッダクリックでの並び替え、入力に追従する絞り込み、行選択など、クライアント側のUI状態を持つ | React Island（`shadcn/ui` の DataTable） |

- htmxで足りる画面をReact Islandにしない。[ADR-0002](../../../decisions/adr-0002-frontend-technology-boundary.md) は「検索フィルター適用後の一覧差し替え、ページネーション、無限スクロール」を明示的にhtmxの用途としている。
- 逆に、UI状態を持つ表をhtmxと自前JSで組み立てない。インタラクティブUIの標準手段はReact Islandsとする。

## 2. 絞り込み・並び替えをどこで行うか

**ページングの有無で決める。件数の感覚で決めない。**

- 全件をクライアントへ渡す画面 — クライアント側で絞り込み・並び替えを行ってよい。
- サーバー側でページングする画面 — 絞り込み・並び替えも必ずサーバー側で行う。

サーバー側でページングしながらクライアント側で並び替えると、現在のページ内だけが並び替わるにもかかわらず、ユーザーには全体が並び替わったように見える。これは表示上の不具合ではなく、誤った情報提示として扱う。DataTableは絞り込み・並び替え・ページングをサーバーへ委譲する構成を取れるため、この組み合わせを避けられる。

一覧の取得がN+1クエリになっていないかは [Quality Recommendations](../../../recommendations/quality.md) を参照する。

## 3. 状態をURLへ反映する

並び替え、絞り込み条件、ページ番号は、クエリパラメータへ反映する。

- リロード、ブラウザバック、URL共有で同じ一覧を再現できる。
- サーバー側で処理する場合、パラメータがそのままクエリの入力になり、状態を二重に持たない。
- パラメータは常にサーバー側で検証する。URLの書き換えで、権限上見えない行や列が見えてはならない（[Architecture Standard](../../architecture/)）。

表示列の切り替えなど、ユーザーごとの表示設定に近いものは、URLへ載せるか永続化するかを画面ごとに決めてよい。

## 4. 揃える操作

- 絞り込みUIは表の上部にまとめる。行や画面の各所へ散らさない。
- 並び替えは列ヘッダから行い、現在どの列で昇順・降順に並んでいるかが見て分かるようにする。
- ページネーションは表の下部に置く。
- 一覧に対する主操作（新規作成等）はPage Header領域へ置く。行に対する操作は当該行内へ置く（[Core Standard](../README.md)）。
- 行選択を持つ場合、選択状態が絞り込みやページ移動で意図せず失われないようにするか、失われることをユーザーへ明示する。

## 5. データがない場合

Core StandardのEmpty Stateに従い、次の2つを区別する。

- **元データが0件** — 次に取れる操作（新規作成など）を示す。
- **絞り込み結果が0件** — 条件を緩める、または解除する手段を示す。同じ「データがありません」で済ませない。

## 6. 配線の共通化

DataTableはheadlessなエンジンの上に構築するため、並び替え・絞り込み・ページングの配線と、そのためのUI（ヘッダのソート操作、検索入力、ページャ）は画面側のコードになる。したがって画面が増えるほど同じ配線が重複する。

- 同じ配線が実際に繰り返された時点で、プロジェクト内の共通コンポーネントへ寄せる。1画面目では分離しない。
- 共通化する対象は配線と操作の一貫性であり、業務ドメインの知識を持ち込まない（[Core Standard](../README.md) のDomain Components）。
- 採用済みのApplication UI Kitに実装がある場合は再実装しない。
