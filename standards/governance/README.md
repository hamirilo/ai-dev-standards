# Governance & Rules

本ドキュメントは、「人およびAIエージェントはどう行動するか」という開発時の行動規範・ルールを定義します。
「システムをどう作るか」という技術的な内容は [Architecture Standard](../architecture/) を参照してください。

---

## 1. 開発原則と逸脱ルール

- **Standardは強いデフォルト**: 原則として本リポジトリで定義されたArchitecture / Application UI Standardに従う。
- **重要な逸脱だけ記録する**: Standardから外れること自体は禁止しないが、将来「なぜこのプロジェクトだけ違うのか」が問題になる重要な逸脱は、プロジェクト側ADR等で理由を記録する。軽微な例外には不要。
- **Standardを増やすこと自体を目的にしない**: 同じ判断や説明が複数プロジェクトで繰り返され、統一しないことで実際の問題が起きるものを優先して標準化する。

### 1.1. Standard追加時の分類

新しいルールを追加する前に、次のどこに属するかを判断します。

- **Core Standard**: 対象プロジェクトの大半に適用し、適用しない方が例外となる、変わりにくい判断。
- **Optional Standard**: 特定機能を採用した場合だけ必要になるが、その機能では詳細な共通契約・判断が有効なもの。
- **Recommendation**: 迷いを減らすための推奨候補。Standardほどの強制力を持たせないもの。
- **Shared implementation**: 判断ではなく、複数プロジェクトで繰り返す実装。
- **Project specific**: 1プロジェクト固有の要件・選択。
- **ADR**: 重要な決定の理由・背景を残すもの。

「将来使うかもしれない」だけではStandard追加の理由にしません。
詳細は [ADR-0004](../../decisions/adr-0004-core-and-optional-standards.md) を参照してください。

## 2. AI利用方針

### 2.1. モデル選定

タスクの難易度に応じてAIモデルのティアを使い分けます。

- **軽量ティア (Light)**: テスト実行・ログ収集・単純検証。
- **標準ティア (Standard)**: 通常の実装・ドキュメント作成・一般的なコードレビュー（デフォルト）。
- **高性能ティア (High Performance)**: 複雑なアーキテクチャ設計・高度な難関バグ調査。高性能モデルへの引き上げはユーザーの承認を推奨。

### 2.2. コンテキスト・探索の抑制

- **不要なファイル探索の禁止**: タスクに関連しないソースコード全体を無差別に読み込まない。
- **ドキュメントの部分読み**: Core Standardもタスクに関連する範囲を中心に読み、Optional Standardは該当機能を扱う場合のみ読む。

## 3. Git運用・コミットルール

### 3.1. ブランチ戦略

- **main 直接コミット禁止**: 必ず `type/topic/short-description` の形式で作業ブランチを切る（例: `feature/auth/add-oidc`）。
- **1ブランチ = 1目的**: 無関係な変更を混ぜない。
- **マージ方式**: 原則として squash merge で main に取り込む。

### 3.2. AIによるコミット・push

AIは、ユーザーの明示的な許可なく `git commit` / `git push` を行いません。
ただし、現在の依頼に「コミットして」「pushして」「PRを作って」などの明示的な公開指示が既に含まれている場合は、その同一スコープについて二重の承認を要求しません。

変更前後で対象範囲を把握し、無関係な変更を混ぜないことを優先します。

---

## 4. コードレビュー・品質管理

- **セルフチェック**: コミット提案前に、利用可能な静的解析、Formatter、自動テスト等を実行し、自力で修正可能な問題は解消する。
- **無闇な抽象化の禁止**: 「将来必要になるかもしれない」という理由だけで独自ラッパーや過剰な共通化を行わない。
- **自動化の境界線**: Lint / Format / Test / link check等、機械的に安く確実に判定できるものは自動化する。Architecture / UXの妥当性のような判断的事項のために巨大な独自コンプライアンス基盤を作らない。
