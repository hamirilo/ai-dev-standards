# Governance & Rules

本ドキュメントは、「人およびAIエージェントはどう行動するか」という開発時の行動規範・ルールを定義します。
技術的な内容は [Architecture Standard](../architecture/) を参照してください。

---

## 1. Standardと逸脱

- **Standardは強いデフォルト**: 原則として定義済みのArchitecture / Application UI Standardに従う。
- **重要な逸脱のみ記録**: 独自の技術選定や大きなUX変更など、将来「なぜ違うのか」を説明する価値がある逸脱は、プロジェクト側のADR等に理由を残す。軽微な例外には不要。
- **Coreを増やしすぎない**: ほぼすべての対象プロジェクトに適用され、長期間変わりにくい内容だけをCore Standardに置く。
- **機能固有の詳細はOptionalへ**: 監視、ファイルアップロード等、必要なプロジェクトだけが利用する詳細仕様はOptional Standardへ分離する。

新しいStandardを追加する前に、以下を確認します。

1. 複数プロジェクトで同じ判断を繰り返しているか。
2. 統一しないことで実際の運用・UX・保守上の問題があるか。
3. AIへ同じ説明を繰り返しているか。
4. 長期間変わりにくい判断か。

該当しない場合は、Recommendation、Shared UI等の共通実装、プロジェクト固有文書への配置を優先します。
詳細は [ADR-0004](../../decisions/adr-0004-core-and-optional-standards.md) を参照してください。

## 2. AI利用方針

### 2.1. モデル選定

タスクの難易度に応じてモデルのティアを使い分けます。

- **Light**: テスト実行、ログ収集、単純検証
- **Standard**: 通常実装、文書作成、一般的なレビュー（デフォルト）
- **High Performance**: 複雑な設計、難易度の高い障害調査

具体的なモデル名は固定しません。

### 2.2. コンテキスト・探索

- タスクに関係しないソースコードを無差別に読み込まない。
- 最初からすべてのStandardを読まず、Coreから必要な領域だけ読む。
- Optional Standardは、その機能を実装・変更する場合だけ読む。

## 3. Git運用

### 3.1. ブランチ

- mainへ直接コミットせず、作業ブランチを利用する。
- ブランチ名は `type/topic/short-description` 等、目的が分かる形式を基本とする。
- 1ブランチに無関係な変更を混ぜない。
- マージは原則squash mergeを利用する。

### 3.2. AIによるcommit / push

AIは、ユーザーからcommit / pushの権限を明示的に与えられている場合のみ実行します。
現在の依頼自体に「commitして」「PRを作って」等の明示的な指示が含まれている場合、同じ操作について追加の確認を要求しません。

権限が明示されていない場合は、変更内容と影響を提示してから承認を得ます。

---

## 4. コードレビュー・品質管理

- commit / PR前に、利用可能なLint、Formatter、Test等の機械的チェックを実行する。
- 「将来必要になるかもしれない」という理由だけで抽象化や共通化を増やさない。
- 機械的に安く確実に判定できるものは自動化する。
- ArchitectureやUXのような判断を、大規模な独自コンプライアンスツールで機械判定しようとしない。AIと人間によるレビューを基本とする。
- Standardsリポジトリ自体をProject Generator、Deployment Platform、Component Builder等へ拡張しない。
