# Governance & Rules

本ドキュメントは、「人およびAIエージェントはどう行動するか」という開発時の行動規範・ルールを定義します。
「システムをどう作るか」という技術的な内容は [Architecture Standard](../architecture/) を参照してください。

---

## 1. 開発原則と逸脱ルールの規定 (ADR)

* **Standardは「強いデフォルト」**: 原則として本リポジトリで定義されたアーキテクチャ・UIのスタンダードに従うこと。
* **重要な逸脱の記録義務**: Standardから外れること自体は禁止しないが、独自の技術選定やUXを採用するなど**重要な逸脱を行った場合は、プロジェクト側の ADR (Architecture Decision Record) として「なぜ外れたのか」の理由と背景を必ず記録すること**。軽微な例外には不要。

## 2. AI利用方針

### 2.1. モデル選定 (Model Selection)
タスクの難易度に応じてAIモデルのティアを使い分けること。
* **軽量ティア (Light)**: テスト実行・ログ収集・単純検証。
* **標準ティア (Standard)**: 通常の実装・ドキュメント作成・一般的なコードレビュー（デフォルト）。
* **高性能ティア (High Performance)**: 複雑なアーキテクチャ設計・高度な難関バグ調査。高性能モデルへの引き上げはユーザーの承認を推奨。

### 2.2. コンテキスト・探索の抑制
* **不要なファイル探索の禁止**: タスクに関連しないソースコード全体を無差別に読み込まない。
* **ドキュメントの部分読み**: Standardドキュメントは、タスクに必要な領域のみをピンポイントで読むこと。

---

## 3. Git運用・コミットルール

### 3.1. ブランチ戦略 (Feature Branch Flow)
* **main 直接コミット禁止**: 必ず `type/topic/short-description` の形式で作業ブランチを切る（例: `feature/auth/add-oidc`）。
* **1ブランチ = 1目的**: 無関係な変更を混ぜない。
* **マージ方式**: 原則として squash merge で main に取り込む。

### 3.2. AIによるコミット提案ルール
AIエージェントがコミットを行う際は、**必ずユーザーの事前承認を得ること**。
無断での `git commit` および `git push` は絶対禁止とする。

1. 変更完了後、差分（diff）を把握する。
2. ユーザーに変更の要約、影響範囲、コミットメッセージ案を提示する。
3. ユーザーが「Proceed（承認）」した場合のみコミットを実行する。

---

## 4. コードレビュー・品質管理

* **セルフチェック**: コミット提案前に、静的解析(Lint/Formatter)や自動テスト(pytest等)を実行し、自力でエラーを修正しておくこと。
* **無闇な抽象化の禁止**: 「将来必要になるかもしれない」という理由だけで独自のラッパークラスや過剰な共通化を行わない。
* **自動化の境界線**: LintやTestなど機械的に安く確実に判定できるものは自動化するが、設計・UX・Architectureの妥当性評価は、専用のコンプライアンスツールではなく、AIのプロンプト自己判定および人間によるレビューに委ねる。
