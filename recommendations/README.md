# Recommendations

本ディレクトリは、**現時点で推奨するサードパーティライブラリの既定** をまとめた道標です。
Standardではありません。人とAIが同じ用途で毎回調べ直さず、かつメンテナンスされていないライブラリを掴まないための参照先です。

---

## 1. 位置づけと拘束力

- **特に理由がなければ、ここに書かれたものを使う。**
- 逸脱を禁止しない。別の選択をしてよい。
- **逸脱にADRを求めない。** 選定理由をPR説明等へ短く残す程度でよい。
- ここに無い用途は、各プロジェクトで判断する。判断した結果は §4 に従って追記する。

Optional StandardとRecommendationの判別基準は [ADR-0003](../decisions/adr-0003-core-and-optional-standards.md) を正とします。記述ドリフトを避けるため、本ファイルには基準を再掲しません。

---

## 2. ここに書かないもの

- **Standardが既に答えているもの。** 二重管理になり、必ず食い違う。
  - 基本UI Component（Dialog、DatePicker、DataTable、Toast、Combobox等）は [Application UI Standard](../standards/application-ui/) が `shadcn/ui` と決めている。
  - Django、PostgreSQL、uv、Django Ninjaは [Architecture Standard](../standards/architecture/) が決めている。
- **採用実績のない候補、比較表、調査メモ。** ここは実績のある既定を置く場所であり、知識集ではない。
- バージョン固定（lockfileの責務）、使い方のチュートリアル。

---

## 3. 健全性チェック

未収録のライブラリを新しく導入するときは、次を確認する。

- **リポジトリが動いているか。** 最終コミット・Issue/PRへの応答を見る。
- **アーカイブされていないか。**
- ライセンスが許容範囲か（MIT / Apache-2.0 / BSD / ISC 等）。GPL系は再配布上の制約を個別に評価する。
- 既知の重大脆弱性がないか。
- **剥がすコストが局所的か。** アプリ全体へ染み込む場合は導入判断を重くする。
- 用途の大きさに対して妥当か。単機能のために巨大なフレームワークを入れない。
- 同じ用途のライブラリが既にプロジェクトへ入っていないか。

### 最終リリース日だけで判断しない

安定して機能が揃ったライブラリはリリース間隔が長くなる。リリースが止まって見えても、コミットとIssue応答が継続していれば健全と判断してよい。

実例として、Leafletは最終リリースから3年経過しているが、リポジトリは活発でv2開発が進行している。「直近12ヶ月にリリースがあるか」だけを機械的に適用すると誤って切ることになる。

**放棄の判定は、リリース間隔ではなくリポジトリの応答性で行う。**

### AIエージェントへの要求

Recommendationsに無い依存を追加する場合、**導入前に上記チェックの結果を短く提示する。** 黙って追加しない。

---

## 4. 掲載条件

**実際に採用しているもの、または採用を決定して着手しているものだけを載せる。**

未検証の候補を「良さそうだから」で載せない。この条件があることで、掲載されていること自体が「誰かが実際に使う」の保証になる。

まだ誰も採用していない領域を新規に選定する場合は、§3の健全性チェックを実施し、その結果を根拠としてエントリへ記載する。この場合も候補を並べず、既定を1つに決めてから載せる。

比較検討の詳細な経緯は、必要であれば選定したプロジェクト側のADRへ残し、ここには結論と確認日だけを置く。

---

## 5. エントリの書式

用途（やりたいこと）を見出しにする。ライブラリ名やカテゴリでは引けない。人もAIも「動画を再生したい」から探す。

各エントリは次を持つ。

- **既定**: ライブラリ名とURL
- **ステータス**: `推奨` / `様子見` / `非推奨`
- **確認日**: 実際に状態を確認した日付（絶対日付）
- 適用範囲、使わなくてよい場面、併用するもの

### ステータス

| | 意味 |
|---|---|
| `推奨` | 特に理由がなければこれを使う |
| `様子見` | 継続利用してよいが、新規大規模採用の前に状態を確認する |
| `非推奨` | 新規採用しない。移行先を併記する |

---

## 6. 陳腐化の扱い

- 再確認は定期義務にせず、**そのライブラリを新規導入するとき・その領域を触るとき** に行い、確認日を更新する。
- **`非推奨` になったエントリを削除しない。** 移行先とともに残す。AIや新しい参加者が既存プロジェクトの古いコードを見て同じライブラリを再導入するのを防ぐ効果があり、`推奨` エントリより価値が高い場合がある。
