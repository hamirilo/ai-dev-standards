# ADR-0006: イメージはCIで作り、各環境はpullする

**ステータス**: 採用

## コンテキスト

対象4リポジトリ（jazmf-directory / dx-portal / jazmf-lms / jazmf-workflow）は、いずれもDjango + React Islandsという同じ構成だが、フロントエンドの成果物をどこで作り、イメージをどこでビルドするかが3通りに分かれていた。Standard側にコンテナと配布の記述が無く、リポジトリごとに別々の結論に達していた。

| リポジトリ | フロント成果物を作る場所 | イメージへの入り方 |
|---|---|---|
| jazmf-lms / jazmf-workflow | イメージの中（multi-stage） | ビルドステージからCOPY |
| dx-portal | 開発機 | ビルド前のソースに混ぜてCOPY（成果物は未コミット） |
| jazmf-directory | 本番サーバ | イメージ外。静的配信で参照 |

4リポジトリともイメージをレジストリへpushしておらず、各環境でビルドしている。この構成で実際に次が起きた。

1. **本番でしか出ない依存取得の失敗**: jazmf-directoryのjustfileには「本番は社内HTTPプロキシ経由でしか外に出られず、パッケージレジストリへのfetchが400で落ちることがある」と記録され、回避策（インストールを飛ばす、tarballを手動移送する）が運用手順に入っている。ビルドを本番で行うために、本番のネットワーク制約がデプロイの失敗として現れている。
2. **成果物が欠けたイメージが「成功」として作られる**: dx-portalはビルド時の`collectstatic`を`2>/dev/null || true`で実行していたため、設定が読めず静的ファイルが1つも集まらない状態でもビルドが成功していた。
3. **CIが緑でもイメージがビルドできない**: jazmf-lmsは、テスト・Linter・型チェック・`check --deploy`のすべてが緑のまま、本番イメージのビルドが2つの理由（設定読み込みの失敗、私設レジストリの認証情報がビルドステージに無い）で落ちる状態だった。どのリポジトリのCIもイメージをビルドしていないため、検出できていなかった。
4. **開発機と実行環境のアーキテクチャ差が暗黙**: 各環境でビルドしているあいだは一致するが、ビルド場所を変えた瞬間に問題になる。

いずれも「どこでビルドするか」を決めていないことに起因しており、個別に直しても次のリポジトリで再発する。

## 決定

**成果物は1回だけ作り、各環境はそれを取得して動かす。** 詳細は [Architecture Standard §10](../standards/architecture/README.md#10-コンテナと配布) を正とする。

1. **イメージのビルドはCIで行い、レジストリへpushする。各環境はpullして起動する。** サーバ上でのビルドを通常運用にしない。
2. **フロントエンドの成果物はイメージの中でビルドする。** 開発機やサーバで作った成果物をイメージへ持ち込まない。
3. **イメージがビルドできることをCIで検証する。** テストや型チェックの緑はビルドの成功を意味しない。
4. **実行環境と同じプラットフォームを明示する。**
5. **私設レジストリの認証情報は、CIとビルドの両方に用意し、イメージのレイヤには残さない。** パッケージの可視性は参照側から読める最小の範囲にする。
6. **ビルド時に設定を読み込むコマンドには、ビルド専用の値を明示して渡す。** 実行時の既定値（sqliteへのフォールバック等）を設定に仕込んで代替しない。

## 検討した代替案

- **各環境でビルドを続ける（現状）**: サーバへソース・ツールチェーン・認証情報を置く必要が残り、上記1の「本番のネットワーク制約がデプロイ失敗として出る」構造が変わらない。テストしたものと動くものが同一である保証も得られない。
- **開発機でビルドした成果物をコミットしてイメージへ入れる**: ビルドの再現性はレビューできるが、成果物の差分がレビューを埋め、ビルドし忘れも検出できない。
- **CIでビルドするが、レジストリへpushせず各環境で再ビルドする**: 上記3（ビルド不能の検出）は解決するが、1と「テスト済みの成果物を配る」は解決しない。

## 結果

- デプロイは「pullして起動する」に縮む。サーバにビルドツールチェーンと私設レジストリの認証情報を置かなくてよい。
- 本番のネットワーク制約が、デプロイの失敗ではなくCIの設計問題として扱えるようになる。
- ビルドの失敗がPRの時点で見える。
- 実行するイメージが、テストを通したイメージと同一であると説明できる。

### 適用の前提（移行前に確認する）

- **実行環境からレジストリへ到達できること。** 社内プロキシ経由で`ghcr.io`等へ出られない場合は、到達できるレジストリを用意するか、この決定の「逸脱」として扱う。
- **プラットフォームの一致。** 実行環境のアーキテクチャを確認し、CIのビルドで明示する。
- **pullに使う認証情報の配布先。** サーバへ置くのはビルド用ではなくpull用の読み取り資格情報になる。

### 移行の状態（2026-08-26）

4リポジトリはいずれも各環境でビルドしており、この決定は未適用である。適用の順序は、壊れる余地が大きい順（イメージ内でビルドし、かつ私設レジストリに依存するもの）から進める。移行が完了するまでのあいだ、各リポジトリの現状は逸脱として扱い、`decisions/project-context.md` に現在の方式を明記しておく。

## 例外・見直し

実行環境がレジストリへ到達できない、またはイメージの配布が組織のルールで許可されない場合は、サーバ上のビルドを継続してよい。その場合は制約と回避手順をプロジェクト側のADRへ残し、制約が解消したときに戻せる状態にしておく。「移行が面倒」を理由に各環境でのビルドを恒久化しない。
