# ADR-0006: イメージはCIで作り、各環境はpullする

**ステータス**: 採用

## コンテキスト

Django + React Islandsという同じ構成の複数プロジェクトで、フロントエンドの成果物をどこで作り、イメージをどこでビルドするかが3通りに分かれていた。イメージの中でビルドするもの、開発機でビルドした成果物をソースへ混ぜてイメージに入れるもの、実行環境の上でビルドしてイメージの外から配信するものである。Standard側にコンテナと配布の記述が無く、プロジェクトごとに別々の結論に達していた。

いずれのプロジェクトもイメージをレジストリへpushせず、各環境でビルドしている。この構成で実際に次が起きた。

1. **環境側の問題がデプロイの失敗として現れる**: ある環境でのみ依存の取得が失敗した。原因は環境側の設定だったが、ビルドをその環境で行っていたため、切り分けと修正もその環境上で行うことになった。
2. **成果物が欠けたイメージが「成功」として作られる**: ビルド時の`collectstatic`の失敗を握り潰していたため、設定が読めず静的ファイルが1つも集まらない状態でもビルドが成功していた。
3. **CIが緑でもイメージがビルドできない**: テスト・Linter・型チェック・デプロイ用チェックのすべてが緑のまま、本番イメージのビルドが2つの理由（設定読み込みの失敗、私設レジストリの認証情報がビルドステージに無い）で落ちる状態だった。CIがイメージをビルドしていないため検出できていなかった。
4. **開発機と実行環境のアーキテクチャ差が暗黙**: 各環境でビルドしているあいだは一致するが、ビルド場所を変えた瞬間に問題になる。

いずれも「どこでビルドするか」を決めていないことに起因しており、個別に直しても次のプロジェクトで再発する。

## 決定

**成果物は1回だけ作り、各環境はそれを取得して動かす。** 詳細は [Architecture Standard §10](../standards/architecture/README.md#10-コンテナと配布) を正とする。

1. **イメージのビルドはCIで行い、レジストリへpushする。各環境はpullして起動する。** サーバ上でのビルドを通常運用にしない。
2. **フロントエンドの成果物はイメージの中でビルドする。** 開発機やサーバで作った成果物をイメージへ持ち込まない。
3. **イメージがビルドできることをCIで検証する。** テストや型チェックの緑はビルドの成功を意味しない。
4. **実行環境と同じプラットフォームを明示する。**
5. **私設レジストリの認証情報は、CIとビルドの両方に用意し、イメージのレイヤには残さない。** パッケージの可視性は参照側から読める最小の範囲にする。
6. **ビルド時に設定を読み込むコマンドには、ビルド専用の値を明示して渡す。** 実行時の既定値（sqliteへのフォールバック等）を設定に仕込んで代替しない。

## 検討した代替案

- **各環境でビルドを続ける（現状）**: サーバへソース・ツールチェーン・認証情報を置く必要が残る。テストしたものと動くものが同一である保証も得られない。
- **開発機でビルドした成果物をコミットしてイメージへ入れる**: ビルドの再現性はレビューできるが、成果物の差分がレビューを埋め、ビルドし忘れも検出できない。
- **CIでビルドするが、レジストリへpushせず各環境で再ビルドする**: 上記3（ビルド不能の検出）は解決するが、1と「テスト済みの成果物を配る」は解決しない。

## 結果

- デプロイは「pullして起動する」に縮む。サーバにビルドツールチェーンと私設レジストリの認証情報を置かなくてよい。
- ビルドの失敗がPRの時点で見える。
- 実行するイメージが、テストを通したイメージと同一であると説明できる。

### 適用の前提（移行前に確認する）

- **実行環境からレジストリへ到達できること。** 到達できない場合は、到達できるレジストリを用意するか、この決定の「逸脱」として扱う。
- **プラットフォームの一致。** 実行環境のアーキテクチャを確認し、CIのビルドで明示する。
- **pullに使う認証情報の配布先。** サーバへ置くのはビルド用ではなくpull用の読み取り資格情報になる。

### 移行

この決定を採用した時点で、既存プロジェクトは各環境でビルドしている状態にある。適用の順序は、壊れる余地が大きい順（イメージの中でビルドし、かつ私設レジストリに依存するもの）から進める。移行が完了するまでのあいだ、各プロジェクトの現状は逸脱として扱い、プロジェクト側の `decisions/project-context.md` に現在の方式を明記しておく。

## 例外・見直し

実行環境がレジストリへ到達できない、またはイメージの配布が組織のルールで許可されない場合は、サーバ上のビルドを継続してよい。その場合は制約と回避手順をプロジェクト側のADRへ残し、制約が解消したときに戻せる状態にしておく。「移行が面倒」を理由に各環境でのビルドを恒久化しない。
