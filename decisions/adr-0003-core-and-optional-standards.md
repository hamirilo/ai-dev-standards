# ADR-0003: StandardsをCoreとOptionalに分離する

**ステータス**: 採用

## コンテキスト

複数プロジェクトで同じ判断を繰り返さないためにStandardを増やしていくと、個々のルールは有用でも、すべてを全プロジェクト共通のStandardとして積み上げることで次の問題が起きる。

- 小さなプロジェクトまで不要なルールに従う必要が生じる。
- AIがタスク開始時に読むべきドキュメント量が増え、必要な情報へ到達しづらくなる。
- 特定機能だけに必要な詳細仕様がCoreに混ざり、Standard全体の責務が曖昧になる。
- 「Standardに書くこと」が目的化し、過去のPlatformと同じようにリポジトリが肥大化する。

一方、Status APIのレスポンス契約のように、特定機能を使う場合には細部まで統一した方が運用・連携コストを大きく下げられる仕様も存在する。

## 決定

Standardsを **Core Standard** と **Optional Standard** に分離する。

### Core Standard

対象プロジェクトの大半に適用する、少数で変わりにくい判断だけを置く。

Coreへ追加する前に、少なくとも次を確認する。

1. 複数プロジェクトで同じ判断が繰り返されているか。
2. AIへ同じ説明を繰り返しているか。
3. 統一しないことで実際の保守・運用・UX上の問題が起きるか。
4. 対象プロジェクトの大半で適用でき、長期間変わりにくいか。

「将来必要になるかもしれない」だけではCoreへ追加しない。

### Optional Standard

特定機能を採用した場合だけ参照・適用する仕様を置く。

OptionalはCoreより詳細に定義してよい。例えば機械連携では、URL、HTTP status、JSON schema、必須フィールド等まで共通契約として規定できる。

ただし、Optional Standardも単なる知識集にはしない。次のような条件を満たすものを対象とする。

- 同じ機能を複数プロジェクトで実装する可能性・実績がある。
- その機能について毎回同じ仕様判断が発生する。
- 統一することで実装、運用、他システム連携のコストを下げられる。

AIはOptional Standardを先回りしてすべて読まず、該当機能を扱う場合のみ参照する。

## Standard以外への配置

新しい知識や資産をStandardへ追加する前に、次の配置先を検討する。

- 特定ライブラリのデフォルト候補・比較 → **Recommendation**
- 複数プロジェクトで再利用するコード → **Shared implementation**
- UIコンポーネントやUI系ライブラリの推奨 → **Shared UI側**
- 1プロジェクト固有の判断 → **Project側**
- 重要な判断の背景 → **ADR**
- 実際に繰り返しが確認されていない初期構成 → **まだTemplate化しない**

ADRは「何を標準化しないか」を列挙するためには作らない。重要な決定・変更の理由を将来説明する価値がある場合にのみ残す。

## ドキュメント構造

3つのStandards領域は増やさない。

```text
standards/
├── governance/
├── architecture/
│   ├── README.md
│   └── optional/
└── application-ui/
    ├── README.md
    └── optional/    # 必要になった場合のみ
```

各領域の `README.md` をCoreとし、Optionalはその領域配下に置く。
新しいトップレベルStandardカテゴリを安易に追加しない。

## レイアウト等のバリエーション追加

既存Standardに「選択肢」が存在する場合も、用途ごとに選択肢を先回りして増やさない。

例えばApplication UIの標準レイアウトは、まず既存テンプレートを拡張して要件へ対応する。同じ派生パターンが複数プロジェクトで繰り返され、独立した標準として扱う価値が確認された場合にのみ、新しい標準レイアウトへの昇格を検討する。

## 結果

- Coreは短く保ち、通常タスクで必要な判断へ早く到達できる。
- 特定機能に必要な詳細仕様はOptionalとして十分具体的に定義できる。
- Standardの追加と同時に「Standard以外へ置く」という判断が可能になる。
- 新しいルールやテンプレートの追加に入場条件を設け、Standardsの肥大化を抑制できる。
