# ADR-0003: 非同期・定期実行は Django 管理コマンド + ホスト cron を標準とする

**ステータス**: 採用

## コンテキスト
Celery / Redis などのメッセージブローカーを用いた非同期・定期実行環境は、スケーラビリティに優れる一方で、インフラ運用（監視・再起動・障害対応）のコストが大きい。
社内ツールや小中規模のアプリケーションにおいて、そのインフラ構築・維持コストに見合うだけのリアルタイム非同期処理（キュー処理）の要件が存在するかどうかが問われていた。

## 決定
定期実行・重い処理は **Django 管理コマンド (`manage.py`) + ホストの cron** を標準とする。
Celery / Redis などの broker 依存は標準インフラセットに含めない。

新規プロジェクトが定期ジョブを持つ場合は、タスクランナー（例: just, make）等に cron を冪等に登録・解除できるレシピを用意する。

## 理由
- 小中規模のシステム運用（単一DB、シンプルな構成）においては、cron によるバッチ実行が最も運用コストが低い（broker や worker プロセスを増やさずに済む）。
- 現状の一般的なワークロード（日次同期、リマインダー送信、クリーンアップ等）は、すべて cron の実行間隔（最短1分）で十分に要件を満たせる。
- `manage.py` コマンドはテストからの直接呼び出し、標準出力へのロギング、権限周りの実行パス等において既存のDjangoの規約とシームレスに連携できる。

## 結果
- 良い点: 過剰なインフラ依存が排除され、インフラ構築と運用が極めてシンプルになる。
- 悪い点・注意点: **リクエスト内の非同期処理**（ユーザーに即座にレスポンスを返し、裏で重い処理を非同期に行うパターン）は実現できない。「送信直後に裏で重い処理を開始する」ような用途には向かない。
- このようなリアルタイム非同期処理が真に必要なプロジェクトは、そのワークロードを明確にした上で、Celery や Redis の導入に関する新規の ADR を起案すること。
