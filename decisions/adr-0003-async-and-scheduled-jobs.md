# ADR-0003: 非同期・定期処理の基盤を一律に標準化しない

**ステータス**: 採用

## コンテキスト

小規模なDjangoアプリの多くは、通常の同期処理だけで十分に要件を満たす。一方、メール送信、大量データ処理、外部I/O、ファイル変換、定期同期などでは非同期化や定期実行が有効になる。

旧方針では Django 管理コマンド + host cron を標準とし、リアルタイム非同期が必要な場合のみCelery等を例外としていた。しかし、非同期処理自体が存在しないアプリも多く、逆にリアルタイムキューが自然なアプリもあるため、特定の実行基盤を全プロジェクト共通のStandardにすることは過剰な制約になる。

## 決定

非同期・定期処理の **具体的な実行基盤をCore Standardでは固定しない**。

通常のCRUDや短時間で完了する処理は同期処理のままとし、次のような場合に非同期化または定期実行を検討する。

- ユーザー応答を待たせる必要がない処理
- 処理時間が長い、または応答時間が不安定な処理
- 外部I/O、メール送信、ファイル変換、大量データ処理
- 定期同期、集計、メンテナンス
- 失敗時に再試行したい処理

非同期処理を導入した場合は、失敗のログ記録、再実行の考慮、可能な範囲での冪等性、必要に応じた処理状態の可視化を行う。

Celery / Redis / RQ / Django-Q / cron / scheduler等の具体的な方式は、プロジェクト要件に応じて選択する。

## 理由

- 不要なアプリにworkerやbrokerを導入しないため。
- 定期バッチだけのアプリと、リアルタイムキューが必要なアプリでは適切な基盤が異なるため。
- Standardの目的を「技術を揃えること」ではなく「繰り返す判断を減らすこと」に置くため。

## 結果

- 非同期処理が不要なアプリには追加インフラを要求しない。
- Django管理コマンド + cronも引き続き有力な選択肢だが、全案件への強制はしない。
- 特定の非同期方式を複数プロジェクトで繰り返し採用し、詳細仕様を揃える価値が生じた場合はOptional Standardとして切り出すことを検討する。
